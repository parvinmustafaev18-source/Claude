# Контекст проекта MeshPlugin

Файл для продолжения работы на любой машине (в т.ч. из браузерного Claude Code).
Технику команд и слоёв смотри в [README.md](README.md) и в скилле
`.claude/skills/autocad-mesh-plugin-workflow/`. Здесь — то, чего в коде не видно:
принятые решения, отвергнутые пути, грабли и что не проверено.

## Работа с трёх компьютеров (два домашних + рабочий)

Правило для Claude: **в начале сессии `git pull --rebase`, после каждой законченной
правки — commit и `git push`.** Не копить незапушенные коммиты: на другой машине
работа продолжится с того, что лежит на GitHub, и всё неотправленное разойдётся.
Учётные данные сохранены в Windows Credential Manager, push проходит без вопросов.

Скрипты для пользователя: `update.bat` — одна кнопка на весь цикл (забрать
свежий код, включая ветку `claude/*`, собрать, отправить собранную DLL обратно;
где нет Visual Studio — поставить готовую из `dist\`). Отдельные шаги:
`sync.bat` (забрать чужое + отправить своё), `build.bat` (собрать и установить),
`install.bat` (поставить готовую сборку из `dist\` без компиляции). `build.bat`
и `install.bat` понимают ключ `/nopause`, `build.bat` возвращает код 2, если
MSBuild не найден, — этим пользуется `update.bat`. Все в CP866/CRLF, в UTF-8 не пересохранять — cmd.exe их
сломает; в git защищены через `.gitattributes` (`*.bat -text`).

**Рабочий компьютер (21.09.2026): собирать ТАМ можно.** Прав администратора
нет, но они и не нужны: Visual Studio 2022 и AutoCAD 2024 на машине уже стоят,
`build.bat` находит MSBuild через `vswhere`, папку AutoCAD — из реестра, и
кладёт бандл в профиль пользователя. Git поставлен портативно, без админки, в
`%LOCALAPPDATA%\Programs\Git` (в `PATH` пользователя добавлена `...\Git\cmd`).
Репозиторий там — `C:\Users\<пользователь>\MeshPlugin-repo`. Прежняя запись
«Visual Studio там не поставить, собирать нельзя» устарела.

Собранная DLL всё равно публикуется в `dist\` (post-build кладёт её туда при
каждой сборке) и едет через репозиторий: так её ставит `install.bat` там, где
Visual Studio нет. Сборка детерминированная, при неизменном коде файл побайтно
тот же и лишних коммитов не даёт. **Собрал — не забудь закоммитить
`dist/MeshPlugin.dll`, иначе на другом компьютере останется старая версия.**

Сборка и тест возможны только на машине с AutoCAD. В браузерном Claude Code
AutoCAD и MSBuild нет — там только правки кода, ошибки компиляции всплывут при
сборке дома.

## Что это

Плагин AutoCAD (.NET 4.8, x64, C# 7.3) — строит регулярную квадратную КЭ-сетку
фундаментной плиты по чертежу и экспортирует схему в текстовый формат ЛИРА-САПР.
Код: `partial class Commands` в Commands / QuadMesh / MeshCore / LiraExport /
ExportCore / ExportSelfCheck / Geometry / SelfCheck / SelfTest / Check / Defs /
BuildInfo, плюс `SpatialGrid.cs`
(internal-классы `SpatialGrid`, `NodeIndex`, `NodeIndex3`).

Папка `audi-legend` — **посторонний проект**, лежит в этой папке случайно.
С 15.08.2026 она **не в репозитории**: снята с отслеживания и внесена в
`.gitignore` (файлы на диске целы, на GitHub их больше нет). Не редактировать,
не удалять с диска, обратно в git не добавлять. Её же скиллы — `.agents/`,
`.claude/skills/remotion-*`, `mediabunny`, `skills-lock.json` — пока остаются
в репозитории по решению пользователя; не трогать.

## Сборка и тест

Собирать и тестировать можно только на машине с AutoCAD. В облачной среде
(браузерный Claude Code) сборки нет — там только правки кода.

```
"C:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\MSBuild.exe" MeshPlugin.csproj /p:Configuration=Debug /p:Platform=x64
```

Папка AutoCAD ищется автоматически (2019–2026); переопределить — `/p:AcadDir="..."`.
`build.bat` вдобавок берёт папку из реестра (`HKLM\SOFTWARE\Autodesk\AutoCAD` → `AcadLocation`) и кладёт её в переменную
окружения `AcadDir` — MSBuild читает переменные окружения как свойства проекта.
Нужно там, где AutoCAD стоит не в `C:\Program Files\Autodesk` (на втором
домашнем компьютере это `F:\Автокад 2024\AutoCAD 2024\`).
Post-build сам собирает бандл `%APPDATA%\Autodesk\ApplicationPlugins\MeshPlugin.bundle`
из `bundle\PackageContents.xml` + DLL.

**Порядок обязателен: закрыть AutoCAD → собрать → открыть AutoCAD.** Если AutoCAD
открыт, DLL занята, xcopy падает и сборка падает намеренно. Исторически это дало
несколько ложных «не помогло» — тестировали на старой DLL. Каждая команда `LIR*`
печатает штамп сборки (время файла DLL + папку) — сверять с временем сборки.

## Самотест (MPTEST)

Расчёт сетки отделён от чертежа: `MeshCore.cs` — ядро `BuildMeshCore(MeshInput)`
→ `MeshResult`, без Editor/Transaction/Database. Команда осталась тонкой:
промпты, чтение слоёв, снап, отрисовка. Единственное место, где расчёт трогает
чертёж, — обратный вызов `MeshInput.SnapDoors` (двери подтягиваются к УЖЕ
построенной сетке).

**Экспорт тоже отделён от чертежа (23.08.2026).** `ExportCore.cs` — ядро
`BuildExportCore(ExportInput)` → `ExportResult`: планарный граф, элементы,
жёсткости, выдавливание стен и ГОТОВЫЙ текст задачи и легенды. Команда
`LIREXPORT` осталась тонкой: промпты, чтение чертежа, запись двух файлов,
круги `ПРОБЛЕМА`. Метод команды был 796 строк — самый большой в проекте и
единственная часть плагина, которую самотест не трогал.

Теперь трогает: `ExportSelfCheck.cs` прогоняет экспорт на той же сетке, что и
проверка сетки, и требует: элементы ссылаются на существующие узлы и объявленные
жёсткости, у каждого типа КЭ своё число узлов (41/44 — 4, 42 — 3, 10 — 2), нет
вырожденных и одинаковых элементов, документы 0/1/3/4 на месте, число строк в
документах 1 и 4 сходится с числом элементов и узлов, а баланс площадей — в
пределах `MeshTol.AreaBalanceRelTol`. Узлы без элементов не провал, а наблюдение:
элементы внутри отверстий удаляются готовыми, их внутренние узлы убирает
Упаковка схемы в ЛИРЕ.

`MPTEST` гоняет ядро на выдуманных планах (`SelfTest.cs`): контур
прямоугольный / Г-образный / П-образный, случайные отверстия, пилоны-стержни,
отпечатки пилонов и стены; шаг 200–500. План строится по номеру (seed) и только
по нему — провал воспроизводится командой `MPTESTCASE` (чертит план в
текущем чертеже). Оракул — постусловия из `SelfCheck.cs` (числа лежат полями
`MeshResult`) плюс правило «сдвинутый план даёт ту же сетку».

Генератор обязан кормить ядро тем же, что даёт реальный конвейер, поэтому
`SnapPlanToGrid` повторяет снап команды (стены и пилоны-стержни к линиям сетки,
отверстия и отпечатки — нет). Без этого провалы ничего не говорили бы о работе
на настоящем чертеже.

**Прогон без AutoCAD работает** — accoreconsole есть в 2019:

```
"C:\Program Files\Autodesk\AutoCAD 2019\accoreconsole.exe" /i blank.dwg /s run.scr /l ru-RU
```

где `run.scr`: `FILEDIA` 0, `SECURELOAD` 0, `NETLOAD` <путь к DLL>,
`MPTEST`, число планов, первый seed. Вывод — UTF-16 с кириллицей в
CP1251, читать через перекодировку. В `build.bat` пока НЕ включено: самотест
сейчас красный (см. открытые задачи), сборка падала бы всегда.

**Что самотест уже нашёл и что исправлено.** Первый же прогон дал совпадающие
рёбра в 24 планах из 30. Источников оказалось два, оба исправлены 19.08.2026:
`EnsureColumnCornerLinks` добавлял связь «угол пилона → ближайший узел», не
посмотрев, что ровно такая связь у угла уже есть; `SplitSegmentsAtNodes` при
разрезе A-B по узлу C выдавал кусок A-C, который в списке уже лежал (это
означает наложенные коллинеарные отрезки выше по конвейеру, разрез просто
превращал наложение в точный дубликат). Теперь `SplitSegmentsAtNodes` не
выпускает одно ребро дважды и возвращает счётчик отброшенных — он в сводке
построения. На 120 планах совпадающих рёбер больше нет. Правка задела и экспорт:
`LiraExport` зовёт ту же функцию, наложенные пластины в ЛИРУ больше не уедут.

Поворот плана на 90° остаётся НАБЛЮДЕНИЕМ, а не правилом: жадное объединение
треугольников идёт по порядку их появления, поворот его меняет. На 30 планах
совпало 1 — как правило не годится, нужен инвариант устойчивее (площадь, а не
число рёбер).
## Жёсткие правила (нарушать нельзя)

1. Сетка не выходит за контур плиты.
2. Контур пилона не выходит за плиту; внутренность пилона пуста, только точка в центре.
3. Сегменты стен не выходят за контур плиты.
4. При обрезке узлы обязаны садиться на грань отверстия, как на контур плиты.
5. Единицы чертежа — миллиметры. Дуги в контурах не допускаются (ЛИРА их не принимает).
6. **Линии сетки не пересекаются без узла.** Пересечение без общего узла ЛИРА не
   считает связью (планарный граф строится по узлам). Проверяется на итоговой
   сетке `SplitSegmentsAtIntersections` — в каждое пересечение врезается узел;
   оставшиеся (их быть не должно) идут предупреждением в консоль.
7. **Все узлы контура пилона входят в сетку плиты.** Углы и точки мелкой сетки на
   гранях обязаны быть узлами (≥2 инцидентных ребра). Обеспечивается врезкой
   (`SplitSegmentsAtPylonNodes`) и проверяется постусловием
   (`FindUnlinkedPylonNodes`); непривязанные узлы идут в `ПРОБЛЕМА`, а не молчат.

Нарушение п.1–3 останавливает построение: `tr.Abort()` + круги в слое `ПРОБЛЕМА`
отдельной транзакцией (чертёж не меняется, маркеры остаются).

## Решения, к которым не возвращаться

- **DXF-импорт в ЛИРУ — путь закрыт.** ЛИРА игнорирует отрезки слоя
  `LINE_TRIANGULATION` при триангуляции (проверено вживую), и перетриангулирует
  наши квады. Остаёмся в текстовом экспорте (документы 0/1/3/4).
- **Конструктивные блоки (документ 6) — отказ.** Сложнее и с неснятой
  неопределённостью. Вместо них — **раздельные жёсткости**: ключ пластины
  составной, `W<толщина>` для стены и `P<толщина>x<длина>` для пилона, поэтому
  пилон получает свой номер даже при толщине, совпадающей со стеной.
- **Имени/комментария у жёсткости в текстовом формате НЕТ** (проверены документы
  3/9/25/8/17/19 — только числа; имена есть лишь у загружений, ключ 39 в doc 0).
  Взамен рядом с задачей пишется `<ИМЯ>_LIRA_LEGEND.txt` с расшифровкой номеров.
- **Убраны команды `MESHCLEAN`, `MESHCOLUMNSBAR`, `MESHQUALITY`** (23.08.2026, по
  решению пользователя — довесок). Уборка чертежа к сетке отношения не имела;
  пилон-стержень вытеснен `LIRPYLON`; предупреждение о плохих элементах
  печатает сама `LIRBUILD`. Чтение старых чертежей сохранено: точка центра в
  слое `COLUMNS` по-прежнему даёт стержень КЭ 10 при экспорте, слой `ПЛОХИЕ`
  вычищается при построении. `Quality.cs` удалён; `SplitSegmentsAtIntersections`
  и `SegmentCrossingPoint` переехали в `Geometry.cs` — без них не работает
  жёсткое правило 6.
- **Префикс команд — `LIR`, не `MESH`** (20.09.2026, перед выдачей на полевые
  тесты). `MESH` — занятое пространство: в AutoCAD с 2010 года есть `MESH`,
  `MESHSMOOTH`, `MESHREFINE`, `MESHCREASE` и ещё десяток, и наши команды тонули
  среди чужих. Вариант «совсем без префикса» (`QUADMESH`, `WALLSAXIS`) отвергнут:
  пропадает группировка в автодополнении, а общие слова вроде `WALLS` рискуют
  столкнуться с AutoCAD Architecture. Самотест уведён в отдельное пространство
  `MP*` — инженеру он не нужен, а `MPTESTCASE` ещё и чертит выдуманный план в
  активный чертёж. Появилась `LIRHELP`: печатает порядок команд в консоли
  и вставляет его же текстом в чертёж (слой `LIRHELP`, 20.09.2026).
  Старые имена не оставлены псевдонимами намеренно — их никто не успел выучить,
  а в автодополнении они бы остались.

- **Другой тип линии для дверей — отвергнут** (на машине acad.lin локализован,
  штрихи не видны на масштабе плана). Двери обозначаются квадратом 200×200
  в слое `WALL_DOORS_MARKS`.

## Архитектурные тонкости, которые легко сломать

- `splitConstraints` ≠ `cutSegments`. Поперечная ось пилона и перпендикуляры
  через косяки дверей кладутся в `splitConstraints` (разрез ячейки). Если положить
  их в `cutSegments`, `ResolveOverlappingSegments` заблокирует ребро — линия
  «игнорируется».
- `SnapWallsToGrid` не двигает `PILON`-оси, иначе крест разъезжается.
- **Закрепление геометрии: метка `FIX` в имени слоя** (`WALLS(H-200 FIX)`, 06.10.2026,
  по жалобе «не нравится, что программа дотягивает и перемещает линии стен»).
  `IsFixedLayer` ищет **" FIX" с пробелом** — без пробела под правило попал бы слой
  вроде `FIXTURES`. Закреплённое пропускают `SnapWallsToGrid` и `SnapColumnsToGrid`,
  а взамен прямые участки таких осей идут **ЖЁСТКИМИ целями** `BuildGridCoords`
  (`MeshInput.FixedWallSegments` → в один список с кромками отверстий): линия сетки
  садится на ось, и качество не теряется. Просто «не двигать» было бы хуже снапа —
  ось резала бы ячейки в произвольном месте и давала лепестки.
  Метка в слое, а не XData, намеренно: невидимое состояние через месяц не объяснить.
  Разбор имён слоёв от метки не страдает — `LayerHeightRegex` (`H-([\d.,]+)`)
  останавливается на пробеле, `IsWallLayer`/`IsColumnLayer` смотрят префикс.
  НЕЛЬЗЯ закреплять `MESH_PYLONS`: он опознаётся точным сравнением имени, и
  переименование убило бы отпечаток. `LIRFIX` поэтому берёт только стены и `COLUMNS`.
- **Отпечаток пилона** (`MESH_PYLONS`) — не пустота: сетка плиты внутри есть,
  только своя. **Строится она по линиям сетки ПЛИТЫ** (06.10.2026, третья
  итерация за день): `BuildPylonInnerCoords` берёт координаты `xs`/`ys`, попавшие
  внутрь отпечатка, плюс обе грани и центр. Раньше внутренность делилась
  собственными равными частями независимо от плиты — узлы внутри не совпадали с
  продолжением соседних линий, и ячейки вокруг резались на треугольники (вееры,
  на которые пожаловался пользователь). Линия плиты ближе `MinElementSize` к
  грани или к центру НЕ берётся (дала бы лепесток), поэтому пилон уже шага сетки
  получает прежние 2 части на сторону. Элементы внутри неравные — это осознанная
  плата за прямые линии. Грани остаются МЯГКИМИ целями `BuildGridCoords`, поэтому
  вееры у граней, не попавших на линию сетки, остались; сделать их жёсткими
  (как кромки отверстий) — следующий шаг, обсуждён и не сделан.
  Грани отпечатка идут в `splitConstraints`, узлы
  отпечатка неподвижны в `WeldShortNodes`/`SmoothMesh` (`fixedRegions`), иначе у
  пилона тоньше 200 мм грань приваривается к оси. Ячейка, накрытая отпечатком,
  выбрасывается по ГАБАРИТАМ (`CellInsideAnyRect`): после снапа её углы лежат на
  границе прямоугольника, где «строго внутри» даёт false.
- `voidPolys` = пилоны + отверстия — идёт в `WeldShortNodes` / `CloseOpenNodes` /
  `SmoothMesh`. Чистый `columnPolys` там используется только для границы пустоты.
- Ячейка внутри проёма определяется по **центру** (`CellCenterInsideAnyColumn`),
  не по всем углам: у ячейки на кромке два угла лежат на границе и тест по углам
  срывается, оставляя обрубки-узлы и осиротевшие круги `ПРОБЛЕМА`.
- Элементы внутри отверстий удаляются на уровне **готового КЭ** (центр по узлам),
  а не на уровне грани — центр треугольника/выпуклого четырёхугольника всегда
  строго внутри него, тест не срывается на любой форме проёма.
- 4-узловой КЭ записан «змейкой» `face0 face1 face3 face2`. При счёте площади
  индексы обязательно переупорядочивать, иначе обход даёт «бабочку» и площадь 0.
- **`LIRBUILD` начинается с сохранения чертежа** (`SaveDrawingBeforeWork`, 06.10.2026,
  по просьбе пользователя). Сохранение идёт ДО промптов и ВНЕ транзакции (внутри
  открытой транзакции базу сохранять нельзя) через `Database.SaveAs(db.Filename,
  DwgVersion.Current)`. Смысл — точка возврата: на диске остаётся состояние до
  построения. Чертёж без пути на диске (ни разу не сохранён) — предупреждение, не
  отказ. Побочный эффект `SaveAs`: флаг «есть несохранённые изменения» он не
  снимает, AutoCAD всё равно спросит про сохранение при закрытии.
- **`DrawSegment` назначает слой `LINE_TRIANGULATION` явно** (06.10.2026). До этого
  слой не назначался вовсе и сетка ложилась на ТЕКУЩИЙ слой чертежа — отсюда
  зависания намертво: если текущим оказывался слой стен, следующий `LIRBUILD`
  читал собственную сетку через `GetWallSegments` как десятки тысяч стен, и
  квадратичный цикл в `CloseOpenNodes` (`cutSegments` × все узлы) считался часами.
  Страховка на случай уже испорченных чертежей — `WallSegmentsSanityLimit` (5000):
  команда останавливается с объяснением и выходом БЕЗ `Commit`. Там же команда
  стала идемпотентной: свои отрезки помечаются XData `MESHPLUGIN_GRID`, и повторный
  запуск стирает прошлую сетку по этой метке (`EraseOwnMesh`), а не весь слой —
  удалять весь `LINE_TRIANGULATION` нельзя, там же лежат контуры пилонов, чьи
  полилинии `ExplodeColumnContours` уже стёр.
  `LIRLAYERS` после построения теперь нужен только ради контура плиты: `LiraExport`
  берёт толщину только из имени слоя контура (линии он и так берёт из
  `LINE_TRIANGULATION`, `LiraExport.cs:280`). Порядок команд (20.09.2026, поправлен
  пользователем) не менялся — менять его без спроса нельзя. Контур выбирается
  указанием, а не по слою, поэтому `LIRBUILD` и `LIRCHECK` до раскладки работают.
- **Потолок размера ячейки** (`MeshTol.MaxCellFactor` = 1.1, 06.10.2026, по жалобе
  «местами сетка растянулась до 350–400 мм»). Растягивают полосу две вещи: сдвиг
  линии к цели (до `MaxShiftAbs` = 100 мм) и удаление линии ради жёсткой цели
  (полоса почти удваивается). В конце `BuildGridCoords` полоса шире
  `MaxCellFactor × шаг` делится на равные части, число добавленных линий идёт в
  журнал. Шаг тем самым стал обещанием, а не пожеланием. Сварка узлов
  (`WeldShortNodes`, до 100 мм) под этот потолок НЕ попадает — она двигает узлы
  после построения координат; если жалобы на крупные ячейки повторятся, причина там.
- **У кругов `ПРОБЛЕМА` есть подпись** (`ProblemMark`, 06.10.2026, по просьбе
  пользователя: «стороннему пользователю непонятно, в чём именно дело»). Точка
  проблемы едет вместе с текстом причины от места обнаружения до чертежа:
  «стена вне плиты», «самопересечение», «открытый узел», «узел пилона»,
  «не разбито», «дверь не на оси», «грань потеряна» и т. д. Рисует `DrawProblemMarks`
  (круг + `DBText` по центру, стиль `PluginTextStyleName`). Новое место, где
  ставится круг, ОБЯЗАНО принести свой текст — это и есть смысл структуры.
  Длинные подписи вылезают за круг Ø600, и это сознательно: читаемость важнее.
- **Х-пересечения осей режутся в ЭКСПОРТЕ, а не в построении** (`ExportCore`,
  06.10.2026, по жалобе «при пересечении линий стен и пилона не образуется узлов»).
  Жёсткое правило 6 в `LIRBUILD` работает только по линиям СЕТКИ, а осей стен и
  пилонов в сетке нет вовсе: `ResolveOverlappingSegments` снимает линии, лежащие
  вдоль них, и сама ось попадает в граф только в экспорте (`LiraExport.cs:280`
  берёт отрезки из `LINE_TRIANGULATION` И со слоёв стен). Поэтому стена, пересекающая
  ось пилона вне узла, в ЛИРЕ сквозь него проходила: связь шла только через плиту.
  Теперь в `BuildExportCore` после `SplitSegmentsAtNodes` стоит
  `SplitSegmentsAtIntersections` — узел врезается в обе оси, а выдавливание берёт
  узлы по координатам через `NodeIndex3`, поэтому у стены и пилона получается общий
  столбец узлов на всю высоту этажа. Разрез заодно добавляет вершину в грань плиты
  (грани строятся по тем же рёбрам), так что висячего узла не возникает.
  В ЧЕРТЕЖЕ оси остаются целыми: это объекты инженера, плагин их не режет.
- **Локальное утолщение плиты — слой `MESH_THICK(H-<t>)` и команда `LIRTHICK`**
  (07.10.2026, ThickZone.cs). Утолщение — та же плита на той же отметке, только
  толще; в ЛИРУ уходит отдельной жёсткостью пластин, геометрия схемы не меняется.
  **Срединная плоскость НЕ смещается** (эксцентриситет утолщения не моделируется —
  обычное упрощение; точная модель потребовала бы жёстких вставок).
  **Команда правит ГОТОВУЮ сетку, а не строит заново** — по прямому требованию
  пользователя: к моменту появления утолщения сетка уже поправлена руками, и
  перезапуск `LIRBUILD` эту работу выбросил бы. Отсюда весь дизайн: трогается
  только полоса вокруг зоны (габарит + допуск), в чертёж пишется РАЗНИЦА
  (`ApplyMeshSegments`), объект, чья геометрия не изменилась, не перерисовывается
  и сохраняет свой цвет, тип линии и XData. Перерисовать всю сетку было бы проще,
  но тогда каждая линия, начерченная инженером, получила бы метку
  `MESHPLUGIN_GRID` и следующий `LIRBUILD` её бы стёр.
  **Узлы пилонов, отверстий и контура плиты закреплены** (`IsFixedNode`): пилон от
  утолщения не меняется ничем — ни отпечатком, ни жёсткостью. В экспорте это
  выражено ПОРЯДКОМ блоков: зона утолщения раздаёт жёсткости ДО тела пилона, и
  пилон её перебивает (ExportCore.cs). Менять порядок нельзя — это решение
  пользователя, а не случайность.
  Из вложенных зон побеждает самая маленькая по площади.
  Допуск подтяжки больше половины шага сетки выворачивает ячейку наизнанку;
  шага команда не знает (сетка чужая), поэтому берёт медиану длин рёбер и
  предупреждает. Подтяжка двигает узлы только в пределах зоны, поэтому линия
  сетки у границы получает ИЗЛОМ — это цена локальности, альтернатива (сдвиг
  линии целиком) меняла бы сетку по всему плану.
- `LIRLAYERS` обязан пропускать служебные слои (`KeepLayer`). Однажды он уводил
  полилинии проёмов с `MESH_HOLES` → экспорт видел 0 отверстий → веер КЭ 42 в проёмах.

## Грабли окружения

- Python на машине — сторовская заглушка, не работает. Для разбора DXF/файлов
  ЛИРЫ использовать **perl** (`/usr/bin/perl`), он парсит 40 МБ за секунды.
- В perl `z == 0` ложно в булевом контексте — фильтр «плита z=0» писать через
  `abs($z) < 1e-9`.
- Консоль MSBuild выводит кириллицу в другой кодировке — сообщения post-build
  писать латиницей.
- После любых скриптовых массовых правок .cs проверять первые байты файла.
- **MSYS-овские awk/sed/grep из Git Bash съедают CR**: пропустив через них файл
  с CRLF (`.csproj`, `.md`), получишь его целиком в LF и мусорный diff на весь
  файл. Точечные подстановки в таких файлах делать PowerShell'ом через
  `[System.IO.File]::ReadAllText` / `WriteAllText`.
- В perl-регулярках `\\n` (литеральный бэкслеш-n — то есть перевод строки ВНУТРИ
  C#-строки) почему-то не совпадает. Работает `\Q\n\E` либо обход шаблоном
  `[^\n]*`. Потеряно на этом было прилично времени, причина не выяснена.
- **DLL, скачанная браузером, не грузится в AutoCAD** (21.09.2026):
  `FileLoadException ... 0x80131515`, «попытка загрузить сборку из сетевого
  ресурса». Причина — метка зоны (поток `Zone.Identifier`), её ставит
  Windows на всё скачанное. Лечится `Unblock-File` в PowerShell, галочкой
  «Разблокировать» в свойствах файла или копированием `copy /b` (метку не
  переносит). Проверять метку: `dir /r`. Установка через `install.bat` этой
  беды не знает — файл приезжает через git.
- **.NET кэширует неудачную загрузку сборки до перезапуска AutoCAD.** Повторный
  `NETLOAD` после исправления даёт ту же ошибку с НОВЫМ путём в тексте и сбивает
  с толку. Перед повторной попыткой AutoCAD закрыть и открыть.
