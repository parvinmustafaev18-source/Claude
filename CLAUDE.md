# Контекст проекта MeshPlugin

Файл для продолжения работы на любой машине (в т.ч. из браузерного Claude Code).
Технику команд и слоёв смотри в [README.md](README.md) и в скилле
`.claude/skills/autocad-mesh-plugin-workflow/`. Здесь — то, чего в коде не видно:
принятые решения, отвергнутые пути, грабли и что не проверено.

## Работа с трёх компьютеров (два домашних + рабочий)

Правило для Claude: **в начале сессии `git pull --rebase`, после каждой законченной
правки — commit и `git push`.** Не копить незапушенные коммиты: на другой машине
работа продолжится с того, что лежит на GitHub, и всё неотправленное разойдётся.
Учётные данные сохранены в Windows Credential Manager, push проходит без вопросов.

Скрипты для пользователя: `sync.bat` (забрать чужое + отправить своё),
`build.bat` (собрать и установить), `install.bat` (поставить готовую сборку из
`dist\` без компиляции). Все в CP866/CRLF, в UTF-8 не пересохранять — cmd.exe их
сломает; в git защищены через `.gitattributes` (`*.bat -text`).

**На рабочем компьютере нет прав администратора** — Visual Studio там не
поставить, собирать нельзя. Поэтому собранная DLL публикуется в `dist\`
(post-build кладёт её туда при каждой сборке) и едет через репозиторий; на
рабочей машине её ставит `install.bat` в профиль пользователя, без прав админа.
Сборка детерминированная, так что при неизменном коде файл побайтно тот же и
лишних коммитов не даёт. **Собрал — не забудь закоммитить `dist/MeshPlugin.dll`,
иначе на рабочем компьютере останется старая версия.**

Сборка и тест возможны только на машине с AutoCAD. В браузерном Claude Code
AutoCAD и MSBuild нет — там только правки кода, ошибки компиляции всплывут при
сборке дома.

## Что это

Плагин AutoCAD (.NET 4.8, x64, C# 7.3) — строит регулярную квадратную КЭ-сетку
фундаментной плиты по чертежу и экспортирует схему в текстовый формат ЛИРА-САПР.
Код: `partial class Commands` в Commands / QuadMesh / MeshCore / LiraExport /
Geometry / Quality / SelfCheck / SelfTest / Check / Defs / BuildInfo, плюс `SpatialGrid.cs`
(internal-классы `SpatialGrid`, `NodeIndex`, `NodeIndex3`).

Папка `audi-legend` — **посторонний проект**, лежит в этой папке случайно.
С 15.08.2026 она **не в репозитории**: снята с отслеживания и внесена в
`.gitignore` (файлы на диске целы, на GitHub их больше нет). Не редактировать,
не удалять с диска, обратно в git не добавлять. Её же скиллы — `.agents/`,
`.claude/skills/remotion-*`, `mediabunny`, `skills-lock.json` — пока остаются
в репозитории по решению пользователя; не трогать.

## Сборка и тест

Собирать и тестировать можно только на машине с AutoCAD. В облачной среде
(браузерный Claude Code) сборки нет — там только правки кода.

```
"C:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\MSBuild.exe" MeshPlugin.csproj /p:Configuration=Debug /p:Platform=x64
```

Папка AutoCAD ищется автоматически (2019–2026); переопределить — `/p:AcadDir="..."`.
Post-build сам собирает бандл `%APPDATA%\Autodesk\ApplicationPlugins\MeshPlugin.bundle`
из `bundle\PackageContents.xml` + DLL.

**Порядок обязателен: закрыть AutoCAD → собрать → открыть AutoCAD.** Если AutoCAD
открыт, DLL занята, xcopy падает и сборка падает намеренно. Исторически это дало
несколько ложных «не помогло» — тестировали на старой DLL. Каждая команда `MESH*`
печатает штамп сборки (время файла DLL + папку) — сверять с временем сборки.

## Самотест (MESHSELFTEST)

Расчёт сетки отделён от чертежа: `MeshCore.cs` — ядро `BuildMeshCore(MeshInput)`
→ `MeshResult`, без Editor/Transaction/Database. Команда осталась тонкой:
промпты, чтение слоёв, снап, отрисовка. Единственное место, где расчёт трогает
чертёж, — обратный вызов `MeshInput.SnapDoors` (двери подтягиваются к УЖЕ
построенной сетке).

`MESHSELFTEST` гоняет ядро на выдуманных планах (`SelfTest.cs`): контур
прямоугольный / Г-образный / П-образный, случайные отверстия, пилоны-стержни,
отпечатки пилонов и стены; шаг 200–500. План строится по номеру (seed) и только
по нему — провал воспроизводится командой `MESHSELFTESTCASE` (чертит план в
текущем чертеже). Оракул — постусловия из `SelfCheck.cs` (числа лежат полями
`MeshResult`) плюс правило «сдвинутый план даёт ту же сетку».

Генератор обязан кормить ядро тем же, что даёт реальный конвейер, поэтому
`SnapPlanToGrid` повторяет снап команды (стены и пилоны-стержни к линиям сетки,
отверстия и отпечатки — нет). Без этого провалы ничего не говорили бы о работе
на настоящем чертеже.

**Прогон без AutoCAD работает** — accoreconsole есть в 2019:

```
"C:\Program Files\Autodesk\AutoCAD 2019\accoreconsole.exe" /i blank.dwg /s run.scr /l ru-RU
```

где `run.scr`: `FILEDIA` 0, `SECURELOAD` 0, `NETLOAD` <путь к DLL>,
`MESHSELFTEST`, число планов, первый seed. Вывод — UTF-16 с кириллицей в
CP1251, читать через перекодировку. В `build.bat` пока НЕ включено: самотест
сейчас красный (см. открытые задачи), сборка падала бы всегда.

**Что самотест уже нашёл и что исправлено.** Первый же прогон дал совпадающие
рёбра в 24 планах из 30. Источников оказалось два, оба исправлены 19.08.2026:
`EnsureColumnCornerLinks` добавлял связь «угол пилона → ближайший узел», не
посмотрев, что ровно такая связь у угла уже есть; `SplitSegmentsAtNodes` при
разрезе A-B по узлу C выдавал кусок A-C, который в списке уже лежал (это
означает наложенные коллинеарные отрезки выше по конвейеру, разрез просто
превращал наложение в точный дубликат). Теперь `SplitSegmentsAtNodes` не
выпускает одно ребро дважды и возвращает счётчик отброшенных — он в сводке
построения. На 120 планах совпадающих рёбер больше нет. Правка задела и экспорт:
`LiraExport` с `Quality` зовут ту же функцию, наложенные пластины в ЛИРУ
больше не уедут.

Поворот плана на 90° остаётся НАБЛЮДЕНИЕМ, а не правилом: жадное объединение
треугольников идёт по порядку их появления, поворот его меняет. На 30 планах
совпало 1 — как правило не годится, нужен инвариант устойчивее (площадь, а не
число рёбер).
## Жёсткие правила (нарушать нельзя)

1. Сетка не выходит за контур плиты.
2. Контур пилона не выходит за плиту; внутренность пилона пуста, только точка в центре.
3. Сегменты стен не выходят за контур плиты.
4. При обрезке узлы обязаны садиться на грань отверстия, как на контур плиты.
5. Единицы чертежа — миллиметры. Дуги в контурах не допускаются (ЛИРА их не принимает).
6. **Линии сетки не пересекаются без узла.** Пересечение без общего узла ЛИРА не
   считает связью (планарный граф строится по узлам). Проверяется на итоговой
   сетке `SplitSegmentsAtIntersections` — в каждое пересечение врезается узел;
   оставшиеся (их быть не должно) идут предупреждением в консоль.
7. **Все узлы контура пилона входят в сетку плиты.** Углы и точки мелкой сетки на
   гранях обязаны быть узлами (≥2 инцидентных ребра). Обеспечивается врезкой
   (`SplitSegmentsAtPylonNodes`) и проверяется постусловием
   (`FindUnlinkedPylonNodes`); непривязанные узлы идут в `ПРОБЛЕМА`, а не молчат.

Нарушение п.1–3 останавливает построение: `tr.Abort()` + круги в слое `ПРОБЛЕМА`
отдельной транзакцией (чертёж не меняется, маркеры остаются).

## Решения, к которым не возвращаться

- **DXF-импорт в ЛИРУ — путь закрыт.** ЛИРА игнорирует отрезки слоя
  `LINE_TRIANGULATION` при триангуляции (проверено вживую), и перетриангулирует
  наши квады. Остаёмся в текстовом экспорте (документы 0/1/3/4).
- **Конструктивные блоки (документ 6) — отказ.** Сложнее и с неснятой
  неопределённостью. Вместо них — **раздельные жёсткости**: ключ пластины
  составной, `W<толщина>` для стены и `P<толщина>x<длина>` для пилона, поэтому
  пилон получает свой номер даже при толщине, совпадающей со стеной.
- **Имени/комментария у жёсткости в текстовом формате НЕТ** (проверены документы
  3/9/25/8/17/19 — только числа; имена есть лишь у загружений, ключ 39 в doc 0).
  Взамен рядом с задачей пишется `<ИМЯ>_LIRA_LEGEND.txt` с расшифровкой номеров.
- **Другой тип линии для дверей — отвергнут** (на машине acad.lin локализован,
  штрихи не видны на масштабе плана). Двери обозначаются квадратом 200×200
  в слое `WALL_DOORS_MARKS`.

## Архитектурные тонкости, которые легко сломать

- `splitConstraints` ≠ `cutSegments`. Поперечная ось пилона и перпендикуляры
  через косяки дверей кладутся в `splitConstraints` (разрез ячейки). Если положить
  их в `cutSegments`, `ResolveOverlappingSegments` заблокирует ребро — линия
  «игнорируется».
- `SnapWallsToGrid` не двигает `PILON`-оси, иначе крест разъезжается.
- **Отпечаток пилона** (`MESH_PYLONS`) — не пустота: сетка плиты внутри есть,
  только мелкая (~100 мм). Грани отпечатка идут в `splitConstraints`, узлы
  отпечатка неподвижны в `WeldShortNodes`/`SmoothMesh` (`fixedRegions`), иначе у
  пилона тоньше 200 мм грань приваривается к оси. Ячейка, накрытая отпечатком,
  выбрасывается по ГАБАРИТАМ (`CellInsideAnyRect`): после снапа её углы лежат на
  границе прямоугольника, где «строго внутри» даёт false.
- `voidPolys` = пилоны + отверстия — идёт в `WeldShortNodes` / `CloseOpenNodes` /
  `SmoothMesh`. Чистый `columnPolys` там используется только для границы пустоты.
- Ячейка внутри проёма определяется по **центру** (`CellCenterInsideAnyColumn`),
  не по всем углам: у ячейки на кромке два угла лежат на границе и тест по углам
  срывается, оставляя обрубки-узлы и осиротевшие круги `ПРОБЛЕМА`.
- Элементы внутри отверстий удаляются на уровне **готового КЭ** (центр по узлам),
  а не на уровне грани — центр треугольника/выпуклого четырёхугольника всегда
  строго внутри него, тест не срывается на любой форме проёма.
- 4-узловой КЭ записан «змейкой» `face0 face1 face3 face2`. При счёте площади
  индексы обязательно переупорядочивать, иначе обход даёт «бабочку» и площадь 0.
- `MESHLAYERS` обязан пропускать служебные слои (`KeepLayer`). Однажды он уводил
  полилинии проёмов с `MESH_HOLES` → экспорт видел 0 отверстий → веер КЭ 42 в проёмах.

## Грабли окружения

- Python на машине — сторовская заглушка, не работает. Для разбора DXF/файлов
  ЛИРЫ использовать **perl** (`/usr/bin/perl`), он парсит 40 МБ за секунды.
- В perl `z == 0` ложно в булевом контексте — фильтр «плита z=0» писать через
  `abs($z) < 1e-9`.
- Консоль MSBuild выводит кириллицу в другой кодировке — сообщения post-build
  писать латиницей.
- После любых скриптовых массовых правок .cs проверять первые байты файла.
- **MSYS-овские awk/sed/grep из Git Bash съедают CR**: пропустив через них файл
  с CRLF (`.csproj`, `.md`), получишь его целиком в LF и мусорный diff на весь
  файл. Точечные подстановки в таких файлах делать PowerShell'ом через
  `[System.IO.File]::ReadAllText` / `WriteAllText`.
- В perl-регулярках `\\n` (литеральный бэкслеш-n — то есть перевод строки ВНУТРИ
  C#-строки) почему-то не совпадает. Работает `\Q\n\E` либо обход шаблоном
  `[^\n]*`. Потеряно на этом было прилично времени, причина не выяснена.

## Открытые задачи

1. Судьба стен шахты лифта в экспорте: низ висит в пустоте проёма, к плите этого
   уровня не крепится. Решение не принято.
2. «Стены проваливаются через плиту» в ЛИРЕ — причина не ясна; вероятно нет опор
   и коэффициентов постели C1–C2.
3. Экспорт опор и коэффициентов постели C1–C2 — не реализован.
4. Осиротевшие круги `ПРОБЛЕМА`: предложено фильтровать `problemPts` по наличию
   узла в итоговых `innerSegments`. Не сделано.
5. **Сдвиг плана меняет сетку — 10 планов из 120. ПРИЧИНА НАЙДЕНА, не
   исправлено.** Диагноз снят на seed 2 сравнением журнала по этапам: расхождение
   рождается на самом первом этапе, при обрезке неполных ячеек по контуру плиты
   (`ClipPolygonToConvexCell` + `CleanupPolygon`) — 15 треугольников по краю
   против 14. Линия обрезки местами проходит почти ровно по границе ячейки, и
   останется ли от неё узкий лепесток, решают последние знаки мантиссы; при
   переносе плиты они меняются. Завязки на абсолютные координаты в логике НЕТ,
   индексы (`NodeIndex`, `SpatialGrid`) к границам бакетов устойчивы.
   Обе сетки при этом ЗАКОННЫ: во всех 10 планах ни одного нарушения жёстких
   правил ни до, ни после сдвига, разница — 1-2 крошечных элемента у кромки.
   Гнаться за побайтовым совпадением смысла нет, чинить надо причину — п. 6.
6. **Лепестки-слайверы у кромки плиты (качество), НЕ исправлено.** Тот же seed 2
   даёт худший α = 0.08 в ОБОИХ вариантах — сдвиг тут ни при чём. Обрезок у
   кромки выбрасывается, только если его площадь меньше `MeshTol.MinArea`
   (0.001 мм²) или он схлопнулся в `CleanupPolygon` по `MeshTol.Collinear`
   (0.5 мм). Полоса 0.6 мм × 500 мм проходит оба порога и становится КЭ. Нужен
   осмысленный порог (например, кусок тоньше ~5% шага прирезать к соседу, а не
   делать элементом). Это уберёт и большую часть плавания из п. 5, но МЕНЯЕТ
   сетку на реальных объектах — делать только с ведома пользователя.
7. **Найдено самотестом, НЕ исправлено: узлы контура пилона вне сетки** —
   3 плана из 120 (seed 42, 64, 96), до 17 узлов. Нарушено жёсткое правило 7.
   Плагин про это честно пишет и ставит круги `ПРОБЛЕМА`, но правило есть
   правило. Причина по коду не искалась.
8. Самотест, seed 68 из 120: «построение остановлено на жёстком правиле входа».
   Скорее всего дефект ГЕНЕРАТОРА, а не плагина: `SnapPlanToGrid` двигает
   пилон-стержень к линии сетки и может вытолкнуть его за контур плиты. Проверить
   и, если так, не ставить объекты ближе 100 мм к границе.
9. P1/P2: spatial-индекс для главного цикла ячеек и `CloseOpenNodes`; один проход
   чтения чертежа вместо 14; общий код грань→пластина для `LiraExport` и
   `Quality` (~90 строк дублируются осознанно). Разбиение 630-строчного
   `MESHQUADMESH` — сделано (`MeshCore.cs`).
